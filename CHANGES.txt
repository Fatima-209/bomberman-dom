2026-07-19 — Stage 1.2 WebSocket Server Core: completed

What was missing:

    "A client cannot send game events before completing nickname entry."
  Connection handling, player ID assignment, broadcast-to-all /

What changed:
  File: backend/src/websocket/websocket.js
    - Imported getGameState from ../state/gameState.js.
    - Added a guard in the "message" handler, right after the existing
      malformed-message check: any message whose type is not MSG.JOIN is

    individual handlers, so future handlers (move, place-bomb,
    chat-message) automatically get this protection without each one
    re-implementing the check.
  - Matches the existing style/pattern of the malformed-message guard
    directly above it (log a warning, return early).

  - npm install + node backend/src/index.js boots both the HTTP and
    WebSocket servers with no errors.
  - Existing JOIN flow (nickname entry -> JOINED / PLAYER_LIST_UPDATE)

2026-07-19 — Stage 1.3 Disconnect Handling: completed

What was missing:
  ws.on("close") only removed the socket from the connection hub. It did
  not remove the player from gameState.players, did not broadcast the
  updated player list, and had no branching between a lobby-phase and a
  mid-game disconnect.

What changed:
  File: backend/src/handlers/disconnectHandler.js (new)
    - handleDisconnect(playerId): looks up the player in game state and
      branches on state.phase.
    - No-op if the player never completed JOIN, or if the game is
      already GAME_PHASE.GAME_OVER.
    - LOBBY / COUNTDOWN phase: deletes the player from state.players
      outright, then broadcasts the updated list via
      broadcastPlayerList(). If fewer than 2 players remain, resets
      state.lobby.waitSecondsRemaining / countdownSecondsRemaining to
      null, with a TODO marking where Stage 1.4's actual timer
      cancellation will hook in once those timers exist.
    - PLAYING phase (mid-game): keeps the player entry but sets
      player.connected = false (so future win-condition checks can
      still see who's connected/out), then broadcasts the updated list.
      Computes activePlayers = connected && !isOut; if
      activePlayers.length <= 1, leaves a TODO for Stage 3.3's shared
      win-condition function (1 -> that player wins immediately, 0 -> no
      winner). Not implemented yet since that function doesn't exist
      until Stage 3.3.

  File: backend/src/handlers/joingameHandler.js
    - Exported broadcastPlayerList (was module-private) so
      disconnectHandler.js can reuse the exact same
      player-list-broadcast logic instead of duplicating it.

  File: backend/src/websocket/websocket.js
    - Imported handleDisconnect and call it from ws.on("close"), right
      after removeClient(playerId).

Why this approach:
  - Reused broadcastPlayerList rather than writing a second version, so
    there's one source of truth for what a "public player list" looks
    like on the wire.
  - Mid-game disconnects mark the player disconnected instead of
    deleting them, per the doc's requirement that win-condition checks
    must be based on "connected AND lives > 0" — deleting would lose
    that player's lives/isOut history mid-match.
  - Left explicit TODO comments (not silent gaps) for the two pieces
    that depend on stages not built yet: Stage 1.4's timers and Stage
    3.3's win-condition function. Matches the doc's team-workflow note
    to build against stubs for the next stage rather than block on it.

Verified:
  - node --check on all three touched/new files passes.
  - npm install + node backend/src/index.js boots cleanly.
  - Manual two-client test (Alice, Bob join; Alice's socket closes):
    Bob received a player-list-update with Alice removed and the count
    dropped from 2 to 1, confirming the lobby-phase branch works
    end-to-end.

2026-07-19 — Stage 1.4 Waiting Room & Timers: completed

What was missing:
  state.lobby.waitSecondsRemaining / countdownSecondsRemaining existed
  in the state shape but nothing ever set them. No 20s window, no 10s
  "get ready" countdown, no countdown-tick broadcast, no game-start
  broadcast.

What changed:
  File: shared/type.js
    - Added GAME_RULES.LOBBY_WAIT_SECONDS (20) and
      GAME_RULES.COUNTDOWN_SECONDS (10), documented alongside the other
      game constants rather than hardcoded inline.

  File: backend/src/handlers/lobbyTimerHandler.js (new)
    - onPlayerJoined(state): starts the 20s wait timer once 2+ players
      are in state.players; skips straight to the 10s countdown if the
      4th player joins first.
    - onPlayerLeft(state): if the remaining player count drops below 2,
      cancels whichever timer is running, resets state.phase back to
      LOBBY, and broadcasts a countdown-tick with phase "cancelled" so
      clients stop showing a stale countdown.
    - startCountdown() flips state.phase to COUNTDOWN as its first
      statement and both entry points (natural 20s expiry, 4th player
      joining) guard on state.phase before doing anything else - this
      is what prevents the doc's "4th player joins the same instant the
      20s timer fires" case from starting two countdowns: whichever
      path runs first wins, the other's guard clause no-ops.
    - startGame(): flips phase to PLAYING and broadcasts game-start with
      the current player list. map is sent as null with a TODO (Stage 2
      generates it) - matches the doc's "build against stubs for the
      next stage" workflow note.
    - Timer handles (setInterval ids) are kept as module-local
      variables, not on state, so they never leak into anything that
      serializes/broadcasts state.

  File: backend/src/handlers/joingameHandler.js
    - handleJoin now returns true on a successful join (still falls
      through to implicit undefined on every rejection path) so the
      caller knows whether to trigger the timer logic.
    - Exported toPublicPlayer (was module-private) so
      lobbyTimerHandler.js's game-start payload reuses the same
      player-shape logic instead of a second copy.

  File: backend/src/websocket/websocket.js
    - MSG.JOIN case now calls onPlayerJoined(getGameState()) after a
      successful handleJoin().

  File: backend/src/handlers/disconnectHandler.js
    - Lobby-phase branch now calls onPlayerLeft(state) instead of the
      inline "TODO: reset timers" stub that only touched state fields
      without ever having real timers to cancel.

  Frontend:
  File: frontend/network/serverMessageHandler.js
    - Added cases for countdown-tick (updates
      waitSecondsRemaining/countdownSecondsRemaining, or clears both on
      phase "cancelled") and game-start (sets phase to PLAYING, stores
      map/players).
  File: frontend/app/screens/lobbyScreen.js
    - Waiting-room message now reflects the live timer instead of a
      static "waiting for players" string.
  File: frontend/main.js
    - Added a minimal placeholder screen for phase === PLAYING (just
      confirms the transition happened) - Stage 2 replaces this with
      real board rendering, not meant to be the final game screen.

Why this approach:
  - Split "who owns the timers" (lobbyTimerHandler.js) from "who owns
    the join/disconnect flow" (joingameHandler.js / disconnectHandler.js)
    to avoid a circular import: lobbyTimerHandler.js imports
    toPublicPlayer from joingameHandler.js, so joingameHandler.js and
    disconnectHandler.js call into lobbyTimerHandler.js but it never
    calls back into them. websocket.js is what wires join -> timer
    check, keeping the dependency graph one-directional.
  - No new join-blocking logic was added for the "already in
    COUNTDOWN" case - the existing phase !== LOBBY gate in
    joingameHandler.js already rejects it, so a 3rd/4th late join
    during the 10s countdown is naturally refused with the existing
    "game has already started" message. Documented here since the
    subject doesn't say explicitly whether late joins should be
    allowed mid-countdown; this is the interpretation we went with.

  - Scenario: 2 players join (wait timer starts), one disconnects ~3s

  - node --check on every touched/new file passes.

2026-07-19 — Bugfix: dev server didn't fully shut down on Ctrl+C

What was wrong:
  backend/src/index.js called startHttpServer(HTTP_PORT) without
  keeping a reference to the returned http.Server. websocket.js's
  shutdown() (registered on SIGINT/SIGTERM) cleared its ping interval
  and closed the WebSocket server, but had no way to close the HTTP
  server and never called process.exit(). Result: pressing Ctrl+C
  looked like it stopped the app, but the HTTP server kept listening
  on port 3000 forever and the process never actually exited, so the
  next `npm run dev` failed with EADDRINUSE until the old process was
  killed manually.

What changed:
  File: backend/src/index.js
    - Captures the http.Server returned by startHttpServer and passes
      it into startWebSocketServer(port, httpServer).
  File: backend/src/websocket/websocket.js
    - startWebSocketServer now accepts httpServer as a second
      parameter. shutdown() closes httpServer after wss.close()
      finishes, then calls process.exit(0) so the process actually
      terminates instead of hanging with an open listener.

Verified:
  - node --check on both files passes.
  - Ran the server on alternate ports (3001/8081, to avoid clobbering
    a real dev session) and triggered process.emit("SIGINT") in-process
    (OS-level signal delivery isn't reliably testable across the Git
    Bash/Windows PID boundary - MSYS's $! is not the real Windows PID).
    Confirmed both "WebSocket server stopped" and "HTTP server stopped"
    logged, process exited with code 0, and both ports were free
    immediately after - all before a 4s "still alive" sentinel timer
    would have fired.


2026-07-20 — Bugfix: full-page re-render was wiping the nickname input

What was wrong:
  render.js's render() cleared the entire #app container with
  innerHTML = "" and rebuilt the whole vnode tree from scratch on
  every single setState() call, regardless of which piece of state
  changed. Since gameStore has one global subscriber (renderApp in
  main.js), any unrelated state change - most commonly another
  player joining, which broadcasts PLAYER_LIST_UPDATE to every
  connected socket including ones still on the nickname screen -
  triggered a full teardown/rebuild of the current player's screen.

  Combined with the nickname <input> being uncontrolled (no onInput
  handler; typed text lived only in the DOM node's .value, never in
  state.nicknameInput), this meant: if you were mid-typing your
  nickname and another player joined the lobby at the same moment,
  your screen was wiped and rebuilt from state.nicknameInput (still
  ""), silently erasing what you had typed and dropping input focus.
  Reported as "blocking the entry of other players when inputting
  the nickname."

What changed:
  File: frontend/framework/render.js
    - render() is now only used for the very first paint. It still
      clears and builds the container once, but also stores the
      rendered vnode tree (previousVNode) and the container
      (rootContainer) for later use.
    - Added update(newVNode), which is called on every state change
      after the first render. It runs a recursive patch() that
      compares the old vnode tree to the new one and only touches
      the real DOM where something actually changed, instead of
      destroying and recreating everything.
    - patch() reuses the same real DOM node whenever the tag hasn't
      changed, updating only its changed attributes/events and then
      recursing into its children. Text nodes are updated in place.
      Nodes that were added/removed/changed type are still
      created/removed/replaced as needed.
    - addAttributesToElement now also removes checked/disabled/
      selected when their value becomes false, instead of only ever
      adding them - needed so the submit button's disabled state can
      correctly clear once, e.g., isConnected flips back to true.

  File: frontend/framework/index.js
    - Exported update alongside the existing render.

  File: frontend/app/screens/nameenterScreen.js
    - createNicknameScreen now accepts an onNicknameInput callback
      and the nickname <input> has an onInput handler that calls it
      on every keystroke, making the input fully controlled by
      state instead of only being read at submit time.

  File: frontend/main.js
    - Added handleNicknameInput(rawValue), which calls
      gameStore.setState({ nicknameInput: rawValue }) and is passed
      into createNicknameScreen.
    - renderApp() now tracks whether the first render has happened
      (hasRenderedOnce) and calls render() only once, then update()
      for every subsequent store change.

Why this approach:
  - Keeping the same DOM node across re-renders is what preserves
    browser focus - a brand new <input> element, even with the
    right value, is never "focused" from the browser's point of
    view.
  - Making the nickname input controlled (state is the single
    source of truth for its value) means an unrelated re-render now
    correctly sees old value === new value and leaves the input
    alone, instead of overwriting the DOM's live value back to a
    stale state value. Diffing the DOM alone was not enough without
    this - the two changes only fix the bug together.
  - This also moves render.js closer to satisfying the framework
    doc's "Abstracting the DOM" requirement via diffing, and lays
    groundwork for Stage 2.2's requirement to "re-render only tiles
    that changed."

Verified:
  - Two real browser tabs: tab A stayed on the nickname screen while
    tab B joined; player list and 10s countdown stayed in sync
    across both tabs with no visible flicker or teardown.
  - Manually toggled gameStore.setState({ connectionStatus:
    "disconnected" }) / "connected" repeatedly via devtools console:
    confirmed the submit button's disabled attribute is correctly
    added AND removed on each toggle (previously it would only ever
    be added, never removed).

2026-07-21 — Stage 3.3 Lives, Death & Win Condition: completed

What was missing:
  Bombs exploded, destroyed blocks, and broadcast EXPLOSION, but never
  checked whether a player was standing on a blast tile. PLAYER_HIT,
  PLAYER_OUT, and GAME_OVER were defined in the message contract but
  never sent anywhere. The mid-game branch of disconnectHandler.js had
  a TODO waiting for a win-condition function that didn't exist yet.

What changed:
  File: backend/src/handlers/winConditionHandler.js (new)
    - checkWinCondition(state, reason) - the one reusable function the
      doc asks for. No-ops unless state.phase is PLAYING. Filters
      state.players to connected && !isOut; if more than 1 remain,
      does nothing. If exactly 1 remains, that player wins. If 0
      remain (simultaneous elimination/disconnect), it's a draw -
      GAME_OVER is broadcast either way with winnerId/winnerNickname/
      reason ("draw" always overrides the caller's reason when there's
      no winner).

  File: backend/src/handlers/bombHandler.js
    - explodeBomb() now calls applyExplosionDamage() right after the
      EXPLOSION broadcast, then checkWinCondition(state, "last-standing").
    - applyExplosionDamage(): builds a Set of blast-tile coordinates,
      then checks each connected, non-out player's position against it
      ONCE (not once per tile) - this is what guarantees only one life
      is lost per explosion even with overlapping blast ranges from
      multiple directions/bombs. Decrements lives; broadcasts
      PLAYER_OUT if that reaches 0, otherwise PLAYER_HIT with the
      remaining count.

  File: backend/src/handlers/disconnectHandler.js
    - Mid-game branch now calls checkWinCondition(state, "disconnect")
      instead of the old TODO block that computed activePlayers.length
      and did nothing with it.

  Frontend:
  File: frontend/network/serverMessageHandler.js
    - Added PLAYER_HIT (updates the player's lives in state.players),
      PLAYER_OUT (sets lives: 0, isOut: true), and GAME_OVER (sets
      phase to GAME_OVER, stores winnerId/winnerNickname/winReason,
      stops the input game loop) cases.
  File: frontend/state/gameStore.js
    - Added winnerNickname and winReason to initial state alongside
      the existing winnerId.
  File: frontend/app/screens/gameScreen.js
    - buildPlayerPositionMap() now also skips isOut players (was only
      skipping disconnected ones), so eliminated players stop
      rendering as movable/collidable on the board, per the doc's
      requirement.
    - Added createLivesHud() - a small per-player lives readout above
      the board (hearts, struck through once a player is out).
    - Added createGameOverScreen() - shows the winner's nickname or
      "No winner - draw."
  File: frontend/main.js
    - renderApp() now branches to the game-over screen when
      phase === GAME_OVER. Removed the now-dead
      createGameStartedPlaceholder()/gameLoopStarted - the actual
      game-loop start already moved into serverMessageHandler.js's
      GAME_START handler in an earlier commit, so this stub and its
      now-unused startGameLoop/stopGameLoop imports in main.js were
      leftover dead code.
  File: Styles/styles.css
    - .game-screen is now a column flex container (was row-implicit)
      so the lives HUD stacks above the board instead of sitting
      beside it; added .lives-hud / .lives-hud-item.out.

Why this approach:
  - checkWinCondition() lives in its own file with no dependency on
    bombHandler.js or disconnectHandler.js, so both can import it
    without a circular dependency - same pattern as
    lobbyTimerHandler.js from Stage 1.4.
  - Checking "is this player's position in the blast tile set" once
    per player (not once per tile) is what makes "only one life lost
    per explosion, even with overlapping ranges" true by construction
    rather than needing extra bookkeeping.
  - GAME_OVER's reason distinguishes "last-standing" (bomb-caused) from
    "disconnect", but always reports "draw" when there's no winner,
    regardless of which path triggered the check - matches the doc's
    rule that simultaneous elimination and simultaneous disconnect
    follow the same "0 active players, no winner" rule.

Verified (live server + real ws clients):
  - 2 players, Alice bombs her own spawn tile 3 times in a row: got
    player-hit (livesRemaining 2, then 1), then player-out on the 3rd,
    then game-over { winnerNickname: "Bob", reason: "last-standing" }.
    Bob was never hit by Alice's blast (spawn corners are far apart).
  - 2 players, mid-game disconnect: Alice's socket closed after
    game-start; Bob received player-list-update (Alice connected:
    false) followed by game-over { winnerNickname: "Bob", reason:
    "disconnect" }.
  - node --check on every touched/new file passes.

Still not started: power-ups (Stage 3.2), chat (Stage 4.1), FPS
counter (Stage 4.2). Bomb chain-reaction behavior remains implicit
(a bomb caught in another's blast blocks the flame but does not
detonate early) and still isn't explicitly documented as a team
decision, despite the doc asking for one either way.

  them during a match. POWER_UP_SPAWNED/POWER_UP_COLLECTED were
  defined in the contract but never sent.

Why this approach:
  - Bombs/Flames effects needed no new enforcement code at all -
    handlePlaceBomb() already read player.maxBombs and player.flameRange
    directly when placing/sizing a bomb, so incrementing those fields
    on pickup is the entire effect. Speed is different because nothing
    server-side currently paces move frequency; the interval is
    reduced client-side instead, matching the existing architecture
    rather than introducing a new server-side rate limiter for this.
  - Splicing the power-up out of state.powerUps at collection time
    (rather than, say, marking it "collected") is what makes "a power-up
    must disappear once collected so a second player can't also
    collect it" true without any extra bookkeeping - a player who
    reaches an already-spliced tile just finds nothing there.
