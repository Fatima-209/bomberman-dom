2026-07-19 — Stage 1.2 WebSocket Server Core: completed

What was missing:
  Per the project task breakdown (Stage 1.2 - WebSocket Server Core), one
  requirement was still open:
    "A client cannot send game events before completing nickname entry."
  Connection handling, player ID assignment, broadcast-to-all /
  broadcast-except-sender helpers, and malformed-message handling were
  already in place.

What changed:
  File: backend/src/websocket/websocket.js
    - Imported getGameState from ../state/gameState.js.
    - Added a guard in the "message" handler, right after the existing
      malformed-message check: any message whose type is not MSG.JOIN is
      now rejected (logged and dropped) unless the sending playerId
      already exists in state.players — i.e. unless that connection has
      completed nickname entry via handleJoin().
    - JOIN itself is exempt from the gate, since it's the message that
      creates the player entry in the first place.

Why this approach:
  - Reuses the same state.players[playerId] check that
    joingameHandler.js already uses to detect a completed join — no new
    "has this player joined" tracking was introduced.
  - Placed at the dispatch level (websocket.js) rather than inside
    individual handlers, so future handlers (move, place-bomb,
    chat-message) automatically get this protection without each one
    re-implementing the check.
  - Matches the existing style/pattern of the malformed-message guard
    directly above it (log a warning, return early).

Verified:
  - node --check backend/src/websocket/websocket.js passes.
  - npm install + node backend/src/index.js boots both the HTTP and
    WebSocket servers with no errors.
  - Existing JOIN flow (nickname entry -> JOINED / PLAYER_LIST_UPDATE)
    is unaffected, since JOIN is exempted from the new gate.

2026-07-19 — Stage 1.3 Disconnect Handling: completed

What was missing:
  ws.on("close") only removed the socket from the connection hub. It did
  not remove the player from gameState.players, did not broadcast the
  updated player list, and had no branching between a lobby-phase and a
  mid-game disconnect.

What changed:
  File: backend/src/handlers/disconnectHandler.js (new)
    - handleDisconnect(playerId): looks up the player in game state and
      branches on state.phase.
    - No-op if the player never completed JOIN, or if the game is
      already GAME_PHASE.GAME_OVER.
    - LOBBY / COUNTDOWN phase: deletes the player from state.players
      outright, then broadcasts the updated list via
      broadcastPlayerList(). If fewer than 2 players remain, resets
      state.lobby.waitSecondsRemaining / countdownSecondsRemaining to
      null, with a TODO marking where Stage 1.4's actual timer
      cancellation will hook in once those timers exist.
    - PLAYING phase (mid-game): keeps the player entry but sets
      player.connected = false (so future win-condition checks can
      still see who's connected/out), then broadcasts the updated list.
      Computes activePlayers = connected && !isOut; if
      activePlayers.length <= 1, leaves a TODO for Stage 3.3's shared
      win-condition function (1 -> that player wins immediately, 0 -> no
      winner). Not implemented yet since that function doesn't exist
      until Stage 3.3.

  File: backend/src/handlers/joingameHandler.js
    - Exported broadcastPlayerList (was module-private) so
      disconnectHandler.js can reuse the exact same
      player-list-broadcast logic instead of duplicating it.

  File: backend/src/websocket/websocket.js
    - Imported handleDisconnect and call it from ws.on("close"), right
      after removeClient(playerId).

Why this approach:
  - Reused broadcastPlayerList rather than writing a second version, so
    there's one source of truth for what a "public player list" looks
    like on the wire.
  - Mid-game disconnects mark the player disconnected instead of
    deleting them, per the doc's requirement that win-condition checks
    must be based on "connected AND lives > 0" — deleting would lose
    that player's lives/isOut history mid-match.
  - Left explicit TODO comments (not silent gaps) for the two pieces
    that depend on stages not built yet: Stage 1.4's timers and Stage
    3.3's win-condition function. Matches the doc's team-workflow note
    to build against stubs for the next stage rather than block on it.

Verified:
  - node --check on all three touched/new files passes.
  - npm install + node backend/src/index.js boots cleanly.
  - Manual two-client test (Alice, Bob join; Alice's socket closes):
    Bob received a player-list-update with Alice removed and the count
    dropped from 2 to 1, confirming the lobby-phase branch works
    end-to-end.

Status update (Stage 1 — Lobby & Connection):

  1.3 Disconnect Handling   - done (mid-game win-condition trigger is a
                               documented TODO pending Stage 3.3)

2026-07-19 — Stage 1.4 Waiting Room & Timers: completed

What was missing:
  state.lobby.waitSecondsRemaining / countdownSecondsRemaining existed
  in the state shape but nothing ever set them. No 20s window, no 10s
  "get ready" countdown, no countdown-tick broadcast, no game-start
  broadcast.

What changed:
  File: shared/type.js
    - Added GAME_RULES.LOBBY_WAIT_SECONDS (20) and
      GAME_RULES.COUNTDOWN_SECONDS (10), documented alongside the other
      game constants rather than hardcoded inline.

  File: backend/src/handlers/lobbyTimerHandler.js (new)
    - onPlayerJoined(state): starts the 20s wait timer once 2+ players
      are in state.players; skips straight to the 10s countdown if the
      4th player joins first.
    - onPlayerLeft(state): if the remaining player count drops below 2,
      cancels whichever timer is running, resets state.phase back to
      LOBBY, and broadcasts a countdown-tick with phase "cancelled" so
      clients stop showing a stale countdown.
    - startCountdown() flips state.phase to COUNTDOWN as its first
      statement and both entry points (natural 20s expiry, 4th player
      joining) guard on state.phase before doing anything else - this
      is what prevents the doc's "4th player joins the same instant the
      20s timer fires" case from starting two countdowns: whichever
      path runs first wins, the other's guard clause no-ops.
    - startGame(): flips phase to PLAYING and broadcasts game-start with
      the current player list. map is sent as null with a TODO (Stage 2
      generates it) - matches the doc's "build against stubs for the
      next stage" workflow note.
    - Timer handles (setInterval ids) are kept as module-local
      variables, not on state, so they never leak into anything that
      serializes/broadcasts state.

  File: backend/src/handlers/joingameHandler.js
    - handleJoin now returns true on a successful join (still falls
      through to implicit undefined on every rejection path) so the
      caller knows whether to trigger the timer logic.
    - Exported toPublicPlayer (was module-private) so
      lobbyTimerHandler.js's game-start payload reuses the same
      player-shape logic instead of a second copy.

  File: backend/src/websocket/websocket.js
    - MSG.JOIN case now calls onPlayerJoined(getGameState()) after a
      successful handleJoin().

  File: backend/src/handlers/disconnectHandler.js
    - Lobby-phase branch now calls onPlayerLeft(state) instead of the
      inline "TODO: reset timers" stub that only touched state fields
      without ever having real timers to cancel.

  Frontend:
  File: frontend/network/serverMessageHandler.js
    - Added cases for countdown-tick (updates
      waitSecondsRemaining/countdownSecondsRemaining, or clears both on
      phase "cancelled") and game-start (sets phase to PLAYING, stores
      map/players).
  File: frontend/app/screens/lobbyScreen.js
    - Waiting-room message now reflects the live timer instead of a
      static "waiting for players" string.
  File: frontend/main.js
    - Added a minimal placeholder screen for phase === PLAYING (just
      confirms the transition happened) - Stage 2 replaces this with
      real board rendering, not meant to be the final game screen.

Why this approach:
  - Split "who owns the timers" (lobbyTimerHandler.js) from "who owns
    the join/disconnect flow" (joingameHandler.js / disconnectHandler.js)
    to avoid a circular import: lobbyTimerHandler.js imports
    toPublicPlayer from joingameHandler.js, so joingameHandler.js and
    disconnectHandler.js call into lobbyTimerHandler.js but it never
    calls back into them. websocket.js is what wires join -> timer
    check, keeping the dependency graph one-directional.
  - No new join-blocking logic was added for the "already in
    COUNTDOWN" case - the existing phase !== LOBBY gate in
    joingameHandler.js already rejects it, so a 3rd/4th late join
    during the 10s countdown is naturally refused with the existing
    "game has already started" message. Documented here since the
    subject doesn't say explicitly whether late joins should be
    allowed mid-countdown; this is the interpretation we went with.

Verified (live server + real ws clients, not just node --check):
  - Scenario: 4 players join back-to-back -> confirmed zero "waiting"
    phase ticks were ever sent, countdown broadcast exactly
    10,9,8,...,1, game-start received by all four with the full player
    list.
  - Scenario: 2 players, no others join -> confirmed 20 "waiting" ticks
    (20 down to 1), immediately followed by 10 "starting" ticks (10
    down to 1), then game-start. ~31s real-time run.
  - Scenario: 2 players join (wait timer starts), one disconnects ~3s
    in -> confirmed a countdown-tick with phase "cancelled" was
    broadcast, player-list-update dropped to 1, and no further ticks
    arrived in the following 5s (timer does not silently resume).
  - node --check on every touched/new file passes.

Status update (Stage 1 — Lobby & Connection): all four sub-stages
(1.1-1.4) are now done. Stage 1 complete.

Next up: Stage 2 - Map & Movement.

2026-07-19 — Bugfix: dev server didn't fully shut down on Ctrl+C

What was wrong:
  backend/src/index.js called startHttpServer(HTTP_PORT) without
  keeping a reference to the returned http.Server. websocket.js's
  shutdown() (registered on SIGINT/SIGTERM) cleared its ping interval
  and closed the WebSocket server, but had no way to close the HTTP
  server and never called process.exit(). Result: pressing Ctrl+C
  looked like it stopped the app, but the HTTP server kept listening
  on port 3000 forever and the process never actually exited, so the
  next `npm run dev` failed with EADDRINUSE until the old process was
  killed manually.

What changed:
  File: backend/src/index.js
    - Captures the http.Server returned by startHttpServer and passes
      it into startWebSocketServer(port, httpServer).
  File: backend/src/websocket/websocket.js
    - startWebSocketServer now accepts httpServer as a second
      parameter. shutdown() closes httpServer after wss.close()
      finishes, then calls process.exit(0) so the process actually
      terminates instead of hanging with an open listener.

Verified:
  - node --check on both files passes.
  - Ran the server on alternate ports (3001/8081, to avoid clobbering
    a real dev session) and triggered process.emit("SIGINT") in-process
    (OS-level signal delivery isn't reliably testable across the Git
    Bash/Windows PID boundary - MSYS's $! is not the real Windows PID).
    Confirmed both "WebSocket server stopped" and "HTTP server stopped"
    logged, process exited with code 0, and both ports were free
    immediately after - all before a 4s "still alive" sentinel timer
    would have fired.
